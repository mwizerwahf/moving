Developer guide

Read vehicle data from {{ public_url }} to build your own app.

Every reading a vehicle sends is stored and passed on unchanged. You can fetch readings, follow them live, or have them pushed to your server. All three give the same JSON object. Ask the account owner for an API token, then send it with every request:

Authorization: Bearer at_xxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxxx

The reading object

payload is the reading exactly as the vehicle sent it, in the fgt/2.0 format. envelope holds the request-level fields (schema, imei, iccid, fw, boot). derived is added by the gateway: the chosen position, and litres from the tank's calibration.

{
  "id": 1842,
  "device": {"imei": "866123456789012", "name": "Hilux 1", "plate": "RAD 123 A"},
  "received_at": "2026-11-01T09:12:44.512Z",
  "envelope": {"schema": "fgt/2.0", "imei": "866123456789012", "iccid": "8925010000123456789",
               "fw": "3.0.0", "boot": "a1b2c3d4"},
  "payload": {"seq": 42, "ts": "2026-11-01T09:12:40Z", "ts_src": "gnss", "uptime_ms": 215004,
              "gnss": {...}, "cell": {...}, "cell_loc": null, "veh": {...}, "fuel": [...], "q": {...}},
  "derived": {
    "time": "2026-11-01T09:12:40Z", "time_src": "device",
    "position": {"lat": -1.944123, "lng": 30.061233, "src": "gnss", "acc_m": 5.5},
    "fuel": [{"tank": 1, "litres": 45.2, "level_pct": 56.5, "calibrated": true, "note": null}]
  }
}

position.src is gnss (satellite fix) or cell (cell tower, with acc_m often hundreds of metres). position is null when neither is known. litres is null until the tank is calibrated; note says why.

Endpoints

RequestReturns
GET /api/v1/devicesEvery vehicle with its latest reading
GET /api/v1/devices/{imei}One vehicle with its latest reading
GET /api/v1/devices/{imei}/readings?limit=100&before_id=&since=&until=History, newest first. Pass next_before_id back as before_id for the next page. since and until are ISO 8601 times.
GET /api/v1/readings?after_id=0&limit=500&imei=Everything in arrival order. Store next_after_id and call again to stay in sync.
GET /api/v1/readings/{id}One reading
GET /api/v1/devices/{imei}/calibrationsActive calibration profile for each tank
GET /api/v1/stream?imei=&after_id=Live Server-Sent Events, one reading event per new reading
GET /api/v1/healthService check, no token needed

Errors return a status code with {"detail": "..."}: 401 for a missing or revoked token, 404 for an unknown IMEI or reading. The full schema is at /api/docs.

Follow readings live

The stream sends each reading as it arrives, with its id as the event id. If the connection drops, reconnect with the Last-Event-ID header (browsers do this for you) and missed readings are replayed first. A comment line is sent every 15 seconds to keep the connection open.

curl -N -H "Authorization: Bearer $TOKEN" {{ public_url }}/api/v1/stream

id: 1842
event: reading
data: {"id":1842,"device":{...},"payload":{...},"derived":{...}}

Browsers cannot add headers to EventSource, so a browser page may pass ?token= instead. Only do this from your own back end; a token in a web page can be copied.

Receive readings by webhook

The account owner can add your HTTPS address in Settings. Each new reading is POSTed to it as JSON, the same object with "event": "reading.created" added. Answer with any 2xx status within 10 seconds; otherwise the gateway retries with growing waits, up to 10 times. The same reading can arrive twice, so use id to ignore repeats.

Check every request before trusting it. The headers are X-FGT-Timestamp (Unix seconds) and X-FGT-Signature, which is sha256= followed by the HMAC-SHA256 of timestamp + "." + raw body, keyed with the webhook secret. Reject requests whose timestamp is more than 5 minutes old.

import hashlib, hmac, time

def is_genuine(secret: str, timestamp: str, body: bytes, signature: str) -> bool:
    if abs(time.time() - int(timestamp)) > 300:
        return False
    mac = hmac.new(secret.encode(), timestamp.encode() + b"." + body, hashlib.sha256)
    return hmac.compare_digest("sha256=" + mac.hexdigest(), signature)

For unit firmware

Units send fgt/2.0 to POST {{ public_url }}/ingest with their device key in the X-Api-Key header. The answer is {"ok": true, "stored": n, "duplicates": m} with status 200, including for readings already received, so the unit can clear its queue. 400 means the body was rejected and will not be accepted on retry; 401 or 403 means the key or IMEI is wrong.
